# 1. 项目目的

本阶段不是设计完整 AI 系统，也不是证明某一种技术方案正确。

Discovery 阶段只解决四个问题：

1. 客户业务背景中，我们目前真正知道什么？
2. 我们认为可能存在什么供应链问题？
3. 哪些假设需要通过客户访谈、系统检查和数据验证确认？
4. 如果核心假设成立，一个最小 POC 应该验证什么？

项目最终希望回答：

> **在已有数字化系统基础上，AI 是否能够降低制造企业在缺料分析和采购决策中的跨系统查询、人工汇总和信息理解成本？**

---

# 2. 客户背景

云南CY集团有限公司属于装备制造企业，公开业务涉及数控车床、加工中心、自动线等机床产品。

机床制造属于典型离散制造。

与流程制造相比，其业务通常具有：

- BOM 层级复杂；
- 物料种类多；
- 外购零部件多；
- 不同零部件交付周期差异明显；
- 产品配置可能存在差异；
- 供应链协同复杂；
- 单个关键件缺料可能影响整机生产。

因此，生产计划、BOM、库存、采购和供应商交付之间具有较强联动关系。

这使其适合作为制造供应链 AI POC 的模拟对象。

# 6. 关键业务角色假设

Discovery 阶段至少需要识别以下角色：

| 角色 | 主要关注问题 |
|---|---|
| 生产计划员 | 生产任务能否按时齐套 |
| 采购员 | 哪些物料需要采购、采购多少、何时采购 |
| 仓库人员 | 当前库存及实际可用库存是多少 |
| 供应商管理人员 | 供应商交付和质量风险 |
| 供应链负责人 | 整体供应链风险 |
| 审批管理人员 | 是否允许执行采购 |
| IT / 数字化团队 | 系统、接口、权限及数据安全 |

不同角色看到的数据范围和拥有的操作权限可能不同。

因此后续如果进入 POC：

> **AI 权限不得高于当前操作用户权限。**

# 7. 核心假设

本项目当前提出四个待验证假设。

## H1：跨系统查询成本较高

假设：

完成一次缺料分析需要查询多个系统或数据源。

例如：

生产计划；

BOM；

库存；

采购订单；

供应商交期。

### 如果成立

AI可能通过统一交互入口减少信息查询步骤。

### 如果不成立

如果现有 ERP / MRP 已经能够高效完成相关分析，则 AI 的价值需要重新评估。

---

## H2：缺料判断存在人工汇总

假设：

业务人员获取数据之后，仍然需要 Excel 或人工方式进行二次计算和汇总。

### 如果成立

可以考虑：

数据自动获取；

确定性计算；

AI解释。

### 如果不成立

需要寻找其他真正存在人工成本的环节。

---

## H3：部分风险判断依赖业务经验

例如两个物料虽然缺口相同：

A物料有多家供应商，Lead Time较短；

B物料只有单一供应来源，Lead Time较长。

两者真实业务风险并不相同。

假设目前存在一定程度依赖计划、采购或供应链管理人员经验进行风险判断的情况。

### 如果成立

可以考虑将部分经验沉淀为：

> **可解释业务规则 + AI辅助分析。**

### 如果不成立

应优先复用已有业务规则和系统能力。

---

## H4：缺料处理存在较高的信息解释成本

即使系统已经产生一个缺料结果：

业务人员仍可能进一步需要知道：

为什么缺；

什么时候缺；

影响哪些生产任务；

在途物料能否及时到达；

有哪些处理方案；

哪些问题应该优先处理。

假设 AI 在此处能够承担：

> **跨数据源信息组织与结果解释。**

而不是替代确定性计算。

# 10. POC Problem Statement

只有核心假设得到验证之后，才进入 POC。

拟验证的问题定义为：

> **能否让 AI 基于企业已有生产计划、BOM、库存、在途采购和必要供应商信息，完成受控的跨系统数据获取，通过确定性业务规则计算缺料风险，并生成具有数据依据、可解释、可追溯的采购建议？**

其中有三个关键要求：

### 受控

AI只能访问获得授权的数据和工具。

### 可解释

结果必须说明：

使用了哪些数据；

为什么判断存在风险。

### 可追溯

系统必须能够复现：

AI调用了哪些工具；

获取了什么数据；

执行了什么规则；

最终如何形成建议。

# 13. AI 与传统逻辑边界

本项目明确：

> **不是所有问题都应该使用大模型。**

| 问题 | 实现方式 |
|---|---|
| 获取库存 | API / SQL |
| 查询 BOM | API / SQL |
| 查询生产计划 | API / SQL |
| 查询采购订单 | API / SQL |
| 计算需求 | Deterministic Logic |
| 计算缺口 | Deterministic Logic |
| 风险基础评分 | Rule Engine |
| 理解自然语言问题 | LLM |
| 决定调用哪些授权工具 | Agent |
| 综合解释结果 | LLM |
| 最终采购决策 | Human |

核心原则：

> **事实来自业务系统。**

> **数值来自确定性计算。**

> **规则来自业务定义。**

> **LLM负责理解、编排和解释。**

> **人负责关键决策。**

用户提出：

> 下个月计划生产25台某立式加工中心，目前有哪些关键物料存在缺料风险？

↓

# 16. 成功标准

POC成功不能定义为：

> Demo能够运行。

至少需要满足以下条件。

## 数据正确

结构化业务数据必须来自正确数据源。

LLM不得自行生成库存、订单、价格等事实数据。

---

## 计算正确

相同输入条件下：

缺料计算应产生稳定、一致、可复现的结果。

---

## 工具正确

Agent能够选择正确的数据工具和业务工具。

不得出现明显无意义调用或越权调用。

---

## 可解释

关键风险必须包含：

数据依据；

规则依据。

---

## 安全

未经人工批准：

> **禁止发生高风险写操作。**

---

## 业务价值

与当前流程相比：

至少证明一种明确改善，例如：

减少系统切换；

减少人工汇总；

降低分析时间；

提高异常解释效率。

实际 KPI 数值必须在获得客户真实基线以后确定。

---

# 17. POC失败条件

以下情况可能意味着不应该继续扩大 POC。

## 数据不足

关键生产、BOM、库存和采购数据无法可靠获取。

## 数据质量严重不足

主数据无法建立稳定关联。

## 现有系统已经解决问题

如果当前 MRP / ERP 已经能够高效完成全部缺料分析：

不应重复建设。

## 使用频率过低

如果业务发生频率极低：

投入回报可能不足。

## AI没有改善流程

如果引入 Agent 后：

流程更复杂；

执行步骤更多；

业务人员负担反而增加；

则需要重新评估技术方案。

# 21. 项目原则

## Business First

先确认问题是否真实存在。

## Evidence First

严格区分：

事实；

公开陈述；

假设；

未知事项。

## Data Before AI

先确认数据，再设计 Agent。

## Deterministic Before Generative

可以由确定性逻辑可靠完成的问题，不交给 LLM 自由生成。

## Human Owns the Decision

AI提供：

信息；

计算；

解释；

建议。

关键业务决策最终由人负责。

# 22. Discovery阶段结论

基于现有公开信息：

云南CY集团具有较复杂的装备制造业务、上下游供应链关系以及一定数字化建设基础，因此适合作为制造业供应链 AI FDE 项目的模拟对象。

但目前仍然无法确认：

真实 IT 系统架构；

真实 BOM 管理方式；

真实库存与采购流程；

真实供应链痛点；

真实缺料分析方式；

真实供应商管理体系。

因此当前项目状态不是：

> “我们已经知道应该给客户部署什么AI。”

而是：

> **“我们已经形成了一组具有公开背景依据的业务假设，并定义了验证这些假设的方法和进入POC设计阶段的条件。”**

这正是 Discovery 阶段应该达到的状态。
